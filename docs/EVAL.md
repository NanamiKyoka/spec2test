# 评测原则与拒绝过的捷径

## 一、指标定义

| 层 | 定义 | 分母 | 判定方式 |
|---|---|---|---|
| L1 | 输出可解析为 IR schema 的比例（空 message 仍算结构合法） | 8 例 | 结构校验，0/1 |
| L1-cov | 步骤消息覆盖率：非空 `message` 的步骤比例（辅助指标） | 8 例 | 计数 |
| L2 | 「方向+消息」序列对齐（辅助指标） | 7 例（6.7.1.5 无消息交换） | 序列比对 |
| L3 | 具体信令内容 IE 字段命中率（主指标） | 7 例（6.7.1.1 原文为 None） | IE 名集合 recall |

样本量 8，**不报平均数**，只报逐例矩阵。

## 二、已拒绝的捷径（留档备查）

### 1. 用 gold 的同族消息清单驱动 IE 段 —— 否决
跨 RAT 用例（6.7.1.12）的系统得分低于基线时，曾有一条修法：按答案侧（gold）的消息清单来驱动 IE 段生成。**已否决**：这等于把答案的骨架泄露给系统，违反 ADR-0002（遮住答案做评测），一旦实现，全部 L3 数字失去意义。

**采用的合法替代**：候选消息清单只能从 `inputs`（测试目的 + 条款 + 前置条件）中抽取：
正则识别 `SIB1..SIB19`、`SystemInformationBlockTypeN` 与 RRC 消息名；再用**符号表**把输入里出现的
ASN.1 字段（如 `cellReselectionInfoCommon`）反查回所属消息（字段→消息索引）。两者都只读输入与公开
符号表，输入侧看不到答案，因此仍属盲评。

### 2. 用 dry-run 桩结果充当基线 —— 否决
基线曾因 dry-run 被桩覆盖（8 例中 7 例为 mock），该结果作废，基线已重跑。任何"跑出来的数字"必须能追溯到一次真实调用。

### 3. 只报成功用例 —— 否决
失败用例必须保留在表内并附诊断。负项不修饰。

## 三、可复现性
基准由脚本从官方 PDF 重建（`tools/pdf_steps.py`、`tools/pdf_ie.py`），规范正文不入库（ADR-0003）。任何第三方按 README 重跑应得到同一基准。


## 度量口径（最终，2026-10-29 裁定）

- gold 叶子字段 **42**：.10=2 / .12=14 / .2=4 / .3=3 / .4=3 / .5=7 / .6=9（.1 原文 None，不计）
- 去重键 = (消息, 字段名, 归一取值)；同一字段的 GSO/NGSO 条件取值不重复计数（如需更严口径可另报 condition-level recall，本次不报）
- 分母：L1 = 8 例；L3 = 7 例；基线 L3 = **N/A**（基线不产出结构化 IE，0 个字段）

### 4. 条件级 L3（字段 + 取值）—— 暂不采用
gold 的取值大量是 “Same downlink ARFCN…”“Refer to the First cell…” 这类文字引用，不是可归一化的
字面值。试算后 5 个用例全为 0，属于误导性指标。要做需先定义取值归一化本体（枚举 / 数值 / 引用），
两周内不做；主指标仍为字段名 recall。

### 5. 6.7.1.4 的候选召回 —— 维持弃权
6.7.1.4 的输入（TP / 条款 / 前置条件）不含 `SIB19`、`SystemInformationBlockType19` 或其任何字段名；
SIB19 只出现在 gold。用 gold 驱动候选会违反 ADR-0002（遮住答案做评测）。在“只读输入 + 公开符号表”
约束下没有合法信号，因此**弃权是正确行为，不视为失败**，也不计入猜测。

### 6. 结构化基线对照（2026-10-30）

对照协议：同 provider / model / temperature；基线只给输入（TP、条款、前置条件），
不给符号表、候选消息、校验器，也不做修复；每例 1 次调用。产物见 `data/out_baseline_struct/`。

| 用例 | 产品 L3 | 基线 L3（精确） | 基线 L3（relaxed） |
|---|---|---|---|
| 6.7.1.10 | 1.000 | 0.000 | 0.500 |
| 6.7.1.12 | 0.385 | 0.000 | 0.417 |
| 6.7.1.2 | 0.333 | 0.000 | 0.333 |
| 6.7.1.3 | 1.000 | 0.000 | 1.000 |
| 6.7.1.4 | 弃权 | 0.000 | 0.000 |
| 6.7.1.5 | 0.667 | 0.000 | 0.833 |
| 6.7.1.6 | 0.625 | 0.000 | 0.250 |

基线精确 L3 全 0，不是"什么都没写"，而是字段名不带 `-rNN` 版本后缀、或带路径前缀
（如 `cellAccessRelatedInfo.plmn-IdentityList`），与 gold 的精确名不同。relaxed 口径去掉
路径前缀与 `-rNN` 后，基线并不弱：6.7.1.3 打平、6.7.1.5 甚至更高（0.833 vs 0.667）。
因此产品的优势应表述为"ASN.1 精确性 + 确定性可校验 + 允许弃权"，而不是"语义猜得更准"。
主指标保持精确 L3；relaxed 只作诊断，不用于宣称全面领先。

## 符号表口径（NR + LTE 混合）

- 总计 **15 个消息**：NR 7 个（取自 TS 38.331）、LTE 8 个（取自 TS 36.331，供跨 RAT 用例 6.7.1.12 使用）。
- LTE 条目带 `rat: "LTE"` 与 `_partial: true`，**只用于 R1 消息存在性判定**；R2 字段校验对 LTE 跳过，因为字段集只抽了一层、不完整。
- **覆盖范围以入选用例为准，非全量**；后续增加用例需同步扩充符号表，否则会出现"覆盖不足型误报"（已在 6.7.1.12 上实证并修复）。

### 口径变更史（续）
4. 缺陷注入 D2/D3 由“删掉/抹掉单条引用”改为“该 TP 的全部引用”：原实现下同一 TP 仍被其他步骤覆盖，4 条 R3 样本并未真正破坏不变量。重生成 31 条后逐条命中期望规则（31/31），旧 27/31 不再作为结论。

## 七、真实错误集盲测（2026-10-31）

目的：回答“31/31 是不是自建模板自检”。从**真实模型输出**（`data/out_rejected/`、`data/out_baseline_struct/`、`data/out/`）标注 19 条错误，标注在运行前固定；逐条对照 `data/gold_ir/` 与 TS 38.331 ASN.1。复现：`py -3 tools/blindset.py`；结果：`results/blindset/report.md`。

| 口径 | 检出 | 漏检 | 检出率 | 范围内 R1/R2/R3 | 范围外 |
|---|---|---|---|---|---|
| 改动前校验器 | 2 | 17 | 10% | 2/16 | 0/3 |
| 当前校验器 | 16 | 3 | 84% | **16/16** | 0/3 |

**读法**：
- 范围内 16 条全部检出；3 条漏检全部是校验器未声明的范围：方向取值（`N/A`）、步骤顺序（Paging 晚于 SIB25）、消息完整性（缺 SIB4）。不把范围外漏检混进检出率。
- 改动前 R1 只检查 `RRC/SIB/MIB/Paging` 前缀，漏掉 `System Information (...)`、`TN NR Cell 10 configured...`、`E-UTRA SIB1`、`NR SIB1`、`trackingAreaList` 等把说明文字/字段名当消息名的真实错误；改动后对非空、非物理层/NAS 的写法一律判存在性。
- 改动前 R2 只要字段名在全局 ASN.1 集合里就放过，无法发现“字段放错消息”；改动后按消息作用域 + 叶子名判定，并补 11 个自动抽取遗漏的嵌套/别名字段（`manual_review_by_message` / `MESSAGE_FIELD_EXTRA`）。
- 本测试在**产品自己的真实输出** `6.7.1.5` 中查到一条错放字段（`distanceThresh-r17` 放进 SIB2）；已用同一校验器反馈重生成并修正快照。这是“校验器真的会拒收自己”的证据，不是只测模板。

**已知漏检（边界，不计入核心 19 条）**：
1. `ue-Identity` 作为 Paging 顶层 IE：符号表把嵌套字段拍平，R2 目前不区分顶层/嵌套。
2. `ntn-Config` 放在 `NR SIB1` 下：消息名本身被 R1 拒收，整条输出不通过，但字段错位未被单独指出。

## 八、修复闭环与编排消融（2026-11-02）

两个实验都走真实模型通道，产物落在 `data/ab/`，**逐例列出，不报质量平均数**。

### 8.1 修复增益（受控：缺陷注入集）

同一份带缺陷的 IR，分别用「不修复」与「自诊断修复 N 轮」重跑：

```
py -3.12 scripts/ab_repair.py --defects data/defects --arms 0,1
```

每轮流程固定：读校验违规 → 步骤层修 R1/R3（只改 message 与 tp_ref，不允许增删步骤或改 st/actor/direction）
→ 字段层按 R2 反馈重修 → 再校验。无进展立即停止，不烧满轮数。

全量 31 条缺陷，每条跑「不修 vs 修 1 轮」：

| 期望规则 | 样本 | 修复后归零 | 减少但未清零 | 未变 |
|---|---|---|---|---|
| R1 消息存在 | 8 | 5 | 0 | 3 |
| R2 字段作用域 | 7 | 4 | 3 | 0 |
| R3 TP 覆盖 | 16 | 14 | 0 | 2 |
| 合计 | 31 | 23 | 3 | 5 |

未清零的 8 条（逐例）：

| 缺陷 | 规则 | 修复前 | 修复后 |
|---|---|---|---|
| 6.7.1.2_D1 | R2 | 2 | 1 |
| 6.7.1.3_D1 | R2 | 3 | 2 |
| 6.7.1.4_D1 | R2 | 3 | 2 |
| 6.7.1.12_D3 | R3 | 1 | 1 |
| 6.7.1.3_D2 | R3 | 1 | 1 |
| 6.7.1.12_D4 | R1 | 1 | 1 |
| 6.7.1.2_D4 | R1 | 1 | 1 |
| 6.7.1.6_D4 | R1 | 1 | 1 |

读法：
- 不修复时全部按原判定拒收；修复后 23 条归零，3 条减少但未清零，5 条未变。
- 修复只做有依据的定向修改，改不动就停。R1 的 3 条未变是模型没能在允许消息集里找到正确名称，属于能力边界，不记为成功。
- R2 的多违规样本每次最多重修 3 条消息，剩余违规进入拒收；这解释了 2→1、3→2 的部分修复。
- 修复不是重生成：步骤数量与 st / actor / direction 不变，只有 message、tp_ref 或字段变化。

### 8.2 编排消融（固定管线 vs 模型自由编排）

```
py -3.12 scripts/ab_orchestration.py --free-budget 8
```

- 固定管线：`scripts/run_one.py`，阶段顺序写死。
- 自由编排：`scripts/orchestrate.py`，模型在工具白名单里自行决定调用顺序，
  校验/修复工具直接作用于当前产物（模型不必回传整份 IR），预算用尽即停。

全量 8 个用例，自由编排预算 8 次工具调用，固定管线修复 1 轮：

| 用例 | 固定管线 | 自由编排 |
|---|---|---|
| 6.7.1.1 | 通过 · L1 1.0 · L3 — · 调用 9 | 通过 · L1 1.0 · L3 — · 调用 2 |
| 6.7.1.10 | 拒收 · L1 1.0 · L3 1.0 · 调用 2 | 拒收 · L1 1.0 · L3 1.0 · 调用 8 |
| 6.7.1.12 | 通过 · L1 1.0 · L3 0.385 · 调用 3 | 通过 · L1 1.0 · L3 0.385 · 调用 4 |
| 6.7.1.2 | 通过 · L1 1.0 · L3 0.333 · 调用 1 | 通过 · L1 1.0 · L3 0.333 · 调用 2 |
| 6.7.1.3 | 通过 · L1 1.0 · L3 1.0 · 调用 1 | 通过 · L1 1.0 · L3 1.0 · 调用 2 |
| 6.7.1.4 | 弃权 · — · — · 调用 0 | 弃权 · — · — · 调用 0 |
| 6.7.1.5 | 通过 · L1 1.0 · L3 0.667 · 调用 2 | 通过 · L1 1.0 · L3 0.667 · 调用 3 |
| 6.7.1.6 | 通过 · L1 1.0 · L3 0.25 · 调用 4 | 通过 · L1 1.0 · L3 0.25 · 调用 5 |

读法：
- 修好「完成检查」之前，自由编排在 3 个用例上提前宣布完成、产出不完整（判为失败）；
  把缺步骤/缺字段写进状态并拒绝空产物后，8 个用例判定与固定管线一致。
- 判定一致不等于过程相同：自由编排会重复读候选、按需补生成，模型调用数接近（26 次 vs 22 次），
  但耗时显著更高（每一步都要问一次模型；固定管线多次命中缓存）。
- 耗时受缓存影响：固定管线多次命中缓存时接近 0 秒；两组耗时只在同一批次内比较。
- 6.7.1.4 两组都弃权：输入里没有可识别消息名，都不调用模型、不计分。

### 8.3 口径边界

- 自由编排的 `generate_ies` 必须由本次运行的步骤驱动，不会读取历史产物；
  缺步骤或缺字段时判定为 incomplete（失败），不得记为通过。
- 已缓存过的模型响应会让「固定管线」耗时趋近于 0，耗时对比只在同一批次、同一缓存状态下有意义。
- 修复轮数只控制“校验驱动”的修复；结构性 JSON 解析重试固定 1 次，两组一致，避免把语法重试算成修复增益。
