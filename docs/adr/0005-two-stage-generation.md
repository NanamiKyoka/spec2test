# 生成改为两段式（先步骤、再逐消息信令）

**Status: accepted（2026-10-29）** —— 用户指示"先把产品拿出来"，产品当前唯一短板是 L3 打不过基线，故按本方案执行。若 L3 未提升，回退至选项 C。

实测显示：同模型同温度下，**裸 prompt 在 L3 上不弱于本系统**（6.7.1.12 基线 0.231 vs 系统 0.000；6.7.1.5 基线 0.167 vs 系统 0.000；6.7.1.2 打平 0.333），且系统 L1 有两例低于 1（0.545 / 0.429，步骤缺 actor/direction）。归因假设：一次性输出完整 IR，结构化字段挤占了信令 IE 的生成预算。

拟改为两段：①只生成步骤（轻量 JSON）→ ②逐消息生成 IE，每个消息单独一次调用，并注入 TS 38.508-1 默认模板作为起点，输出"模板 + 差分"。

**Why:** 裸 prompt 之所以能赢，是因为模型隐式记得常见消息的默认结构；本系统若显式检索默认模板并做差分，就把这份"隐式记忆"变成可追溯、可校验的推导链——这正是"技术先进性"能落地的地方，也是基线做不到的。
**How to apply:** 若采纳，`generate.py` 拆为 `gen_steps.py` 与 `gen_ie.py`，`score.py` 对两段分别计分；基线保持不变（仍是一次性输出）以保证对比公平。代价约 2 天，从 P3 缓冲与 P4 交付中挤。

## Considered Options
- **B 只放宽约束**（放宽 schema、提高输出上限）：成本低，但不解决"模型不知道默认模板"的根本问题，预计改善有限。
- **C 改主张**（不吹生成，只吹"能判错"）：零成本且完全诚实，但让出 35 分项中"生成"这一核心卖点，且与作品名"编译器"不符。

## 实测结论（2026-10-29）

- **解决了 L1**：两段式后 L1 由 2 例失败（0.545 / 0.429）变为 8/8 = 1.000。原因是单段同时生成步骤与 IE 时，IE 结构常被截断或混入非 JSON 文本。
- **未提升 L3**：系统 0.077–1.000，基线 0.000–0.333，逐例看为 3 胜 / 4 平 / 1 负，无整体优势。根因不在两段式，而在**输入侧信息量**：多个 NTN 用例的 `inputs` 中不出现任何 SIB/消息名（6.7.1.4、6.7.1.12 命中 0 次），而 gold 的 IE 恰恰挂在这些消息上。基线在同一批用例上的高分来自模型先验（见过 SIB19），不是方法优势。
- **结论**：两段式保留（L1 收益确定、可解释），但不作为创新点宣称；L3 的上限由输入信息量决定，须在方案中量化披露。
